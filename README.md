# chckd-lists

Content pipeline for [CHCKD](chckd-context/brand/README.md): sources, tags,
and loads curated "places you've been" checklists (national parks, UNESCO
sites, stadiums, ...) into a DuckDB database.

This is the content pipeline, not the app. It reads
`chckd-context/CHCKD-Taxonomy-Lists.xlsx` and the `registry/` folder,
fetches each list's places from whatever source that list is configured
for (a fixed static list, or a live API), and writes everything into
`data/chckd.duckdb`. Full schema, design rationale, and conventions:
[CLAUDE.md](CLAUDE.md) — read that before making structural changes (new
tables, new hierarchy concepts). This doc is just how to run the thing.

## Setup

One-time, per machine:

```bash
conda env create -f environment.yml   # creates the chckd-lists env (python 3.13)
conda activate chckd-lists
poetry install                         # installs into the conda env — see CLAUDE.md "Environment setup"
```

API keys (only needed for API-backed sources, see "Sources" below):

```bash
cp .env.example .env
# then open .env and paste in your key(s):
#   NPS_API_KEY=...
#   PROTECTED_PLANET_API_KEY=...
```

`.env` is gitignored and loaded automatically — nothing to `export` or
`source`, just fill it in and run the CLI normally. `.env.example` stays
committed as the template for which keys exist.

Every command below assumes `conda activate chckd-lists` is active in your
shell.

## Everyday commands

```bash
chckd-lists migrate       # create/update data/chckd.duckdb from db/schema.sql — run once, and again after a schema.sql change
chckd-lists seed          # (re)generate registry/ from chckd-context/, and load the dimension tables (place taxonomy, list categories)
chckd-lists list          # every registered list, its tier, its status, and which source it's wired to
chckd-lists run <slug>    # run one list end to end (extract -> tag -> categorize -> load), e.g.:
chckd-lists run the-seven-summits
chckd-lists run --all     # run every list whose status is `active` (silently skips `stub` ones)
```

Typical first run on a fresh clone:

```bash
chckd-lists migrate
chckd-lists seed
chckd-lists run --all
```

Every run logs what changed to the console and to `logs/pipeline.log`
(rotating), and records row-level add/remove counts per table in
`table_change_log` — a second run of the same list with nothing new logs
`no change` instead of re-reporting the same rows.

## Where things live

- `registry/lists/tier-1/` .. `tier-5/` — one YAML file per list, grouped
  by the Master List sheet's own tiers. This is what you edit to add,
  configure, or remove a list — see CLAUDE.md "Adding a list" /
  "Removing a list" for the full walkthrough.
- `registry/place_taxonomy.yaml`, `list_categories.yaml` — the
  dimension/hierarchy data, both fully regenerated by `chckd-lists seed`
  (don't hand-edit — edit
  `chckd-context/CHCKD-Taxonomy-Lists.xlsx` instead and re-run `seed`).
  There's no separate `tags.yaml`: a "tag" is just a `place_taxonomy.yaml`
  entry (see CLAUDE.md "Tags are place categories, not a separate
  concept") — tagging a place or list means listing extra taxonomy
  `full_path` strings in its own `tags:` field, not maintaining a second
  vocabulary file.
- `data/chckd.duckdb` — the actual database, gitignored (it's fully
  regenerable from `registry/` + `chckd-context/`, so it's never
  committed). Delete it and re-run `migrate` → `seed` → `run --all`
  whenever you want a clean rebuild.
- `logs/pipeline.log` — rotating log file, gitignored.

## Sources

A list's `source.type` in its registry YAML says how its places get
fetched:

- `static` — a small fixed list of places written directly into the
  registry YAML (e.g. `the-seven-summits.yaml`). No API key needed.
- `nps` — the National Park Service's own API. Needs `NPS_API_KEY`.
- `protected_planet` — the Protected Planet / WDPA API, which covers most
  "US National ___" / state park / wildlife refuge / reserve style lists.
  Needs `PROTECTED_PLANET_API_KEY`. See CLAUDE.md "Protected Planet
  source" — several lists are already wired to this but still
  `status: stub` until someone runs them against a real key and confirms
  the right `designation_id`.

`chckd-lists list` shows every list's current `source` type and `status`
— `status: stub` means don't expect real data yet; `run --all` skips
those on purpose.

## Testing

```bash
pytest
```

Runs the real pipeline (migrate → load dimensions → run a real list → run
it again) against a throwaway DuckDB file, and checks the change log
reports zero rows added on the idempotent re-run.
